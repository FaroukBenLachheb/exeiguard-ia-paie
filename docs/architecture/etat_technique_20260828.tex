\section{R\'esum\'e ex\'ecutif}
% =====================================================================

Ce qui peut \^etre d\'emontr\'e de bout en bout \emph{aujourd'hui}, v\'erifi\'e dans cette session : un dossier salari\'e traverse r\'eellement les 6 \'etats du pipeline (A1 \`a A6, puis TERMIN\'E) via l'API HTTP r\'eelle du service orchestrateur, chaque transition \'etant journalis\'ee dans \path{audit_log} en PostgreSQL --- v\'erifi\'e par appels \texttt{curl} r\'eels contre un conteneur reconstruit \`a partir du code actuel du d\'ep\^ot, puis par une requ\^ete SQL directe (voir \S\ref{sec:orchestrateur}). La suite de tests compl\`ete du d\'ep\^ot (\path{python -m pytest} depuis la racine, avec un vrai PostgreSQL) retourne exactement \textbf{59 passed, 0 failed} (\S\ref{sec:tests-global}).

L'\'ecart principal entre ``ce qui est pr\'evu'' et ``ce qui existe'' n'est pas un manque de code : le Rule Engine (10 r\`egles RG-01 \`a RG-10, 28 tests, tous sourc\'es sur un article pr\'ecis de la CCN SYNTEC ou un accord Soft IT) et le parseur EVP Excel (16 tests) sont r\'eellement impl\'ement\'es et test\'es. L'\'ecart, c'est que \textbf{ni l'un ni l'autre n'est branch\'e sur une route API} : \path{compliance-validation} et \path{extracteur-evp} n'exposent, aujourd'hui, que \path{GET /health} --- confirm\'e en interrogeant directement \path{/openapi.json} sur des conteneurs reconstruits \`a partir du code actuel (\S\ref{sec:extracteur-evp}, \S\ref{sec:compliance}). La machine \`a \'etats de l'orchestrateur ne fait donc, pour l'instant, que changer un statut en base : aucune de ses transitions n'appelle r\'eellement l'extracteur, le Rule Engine, un mock Sage ou le RAG. \path{integration-sage} n'a aucune logique au-del\`a de \path{/health}. Le RAG (\path{POST /rag/query}) est le seul service dont la logique m\'etier est expos\'ee en API, mais il ne poss\`ede \textbf{aucun test automatis\'e} et n'a pas pu \^etre r\'e-ex\'ecut\'e dans cette session (Qdrant/Ollama non disponibles sur cette machine, \S\ref{sec:rag}).

D\'ecouverte propre \`a cette session (\S\ref{sec:dette}) : les conteneurs Docker qui tournaient d\'ej\`a sur cette machine au d\'emarrage de la v\'erification \'etaient construits depuis des images vieilles de 2 \`a 3 semaines et ne refl\'etaient pas du tout le code actuel (\path{POST /dossiers} y r\'epondait 404 Not Found). Ils ont d\^u \^etre reconstruits pour que les v\'erifications de ce rapport portent sur le code r\'eellement pr\'esent dans le d\'ep\^ot aujourd'hui.

\section{Points de vigilance et dette technique d\'ecouverts pendant cette v\'erification}
\label{sec:dette}
% =====================================================================

\begin{itemize}[leftmargin=1.3em]

\item \textbf{Conteneurs Docker locaux p\'erim\'es (d\'ecouverte de cette session).} Au d\'ebut de cette v\'erification, trois conteneurs autonomes (\path{exeiguard-orchestrateur}, \path{exeiguard-extracteur-evp}, \path{exeiguard-postgres}) tournaient d\'ej\`a sur cette machine, construits depuis des images datant respectivement du 7 et du 10 ao\^ut 2026 --- soit avant l'impl\'ementation r\'eelle de la machine \`a \'etats (commit \path{791747c}, 25 ao\^ut). Un appel r\'eel \`a \path{POST /dossiers} contre ce conteneur a retourn\'e \path{404 Not Found}, et \path{/openapi.json} ne listait que \path{['/health', '/db-check']}. Ces conteneurs ont \'et\'e arr\^et\'es et les 4 images applicatives reconstruites (\path{docker compose -f docker-compose.dev.yml build}) pour que les v\'erifications de ce rapport portent sur le code actuel. Cela signifie qu'un simple \path{docker compose up} sans \path{--build} sur cette machine aurait servi, silencieusement, une version du service vieille de trois semaines.
\item \textbf{Identifiants PostgreSQL divergents.} Le mot de passe PostgreSQL r\'eellement configur\'e sur le conteneur local (\path{faroukxabdou}) ne correspond ni \`a la valeur document\'ee dans \path{.env.example} (\path{exeiguard_paie}) ni au d\'efaut cod\'e en dur dans \path{db/database.py} (\path{changeme_local}). Aucun fichier \path{.env} n'existe sur cette machine ; la valeur r\'eelle vient donc d'une variable d'environnement pass\'ee manuellement lors d'un lancement pr\'ec\'edent, non trac\'ee dans le d\'ep\^ot. Source de friction probable pour quiconque relance la stack sans conna\^itre cette valeur.
\item \textbf{Collecte pytest fragile sans \path{DATABASE_URL}.} Confirm\'e dans cette session : lancer \path{python -m pytest} depuis la racine sans variable \path{DATABASE_URL} point\'ee vers un PostgreSQL joignable fait \'echouer la \textbf{collecte compl\`ete} (pas seulement les tests orchestrateur), car \path{orchestrateur/tests/test_e2e_a1_a6.py} appelle \path{init_db()} au niveau module, donc au chargement, avant m\^eme l'ex\'ecution d'un test.
\item \textbf{\path{GRILLE_SYNTEC_ETAM} tr\`es incompl\`ete} (2 entr\'ees) : RG-03 se rabat silencieusement sur une v\'erification de bornes globales (240-500) pour toute position ETAM non couverte, ce qui est \emph{moins pr\'ecis} qu'une v\'erification position/coefficient exacte --- comportement document\'e et volontaire dans le code, mais \`a garder en t\^ete pour ne pas sur-interpr\'eter un r\'esultat ``CONFORME'' de RG-03 sur un profil ETAM comme une v\'erification compl\`ete.
\item \textbf{\path{@app.on_event("startup")} d\'epr\'eci\'e.} \path{orchestrateur/app/main.py} utilise l'API FastAPI \path{on_event}, marqu\'ee \path{DeprecationWarning} par la version de FastAPI install\'ee dans cette session (au profit des \path{lifespan} handlers). Fonctionnel aujourd'hui, mais \`a migrer avant qu'une future version de FastAPI ne la retire.
\item \textbf{R\'eponse \path{/health} incoh\'erente entre services.} \path{orchestrateur} retourne \path{\{"status": "ok"\}} (sans champ \path{service}), les 3 autres services retournent \path{\{"status": "ok", "service": "<nom>"\}} --- incoh\'erence mineure mais qui rend le monitoring g\'en\'erique (un seul contr\^ole pour les 4 services) l\'eg\`erement plus complexe qu'il ne devrait l'\^etre.
\item \textbf{Rag non testable hors VM cible.} \path{rag/config.py} documente explicitement que \path{OLLAMA_HOST}/\path{QDRANT_HOST} doivent \^etre surcharg\'es en \path{localhost} pour tourner hors du r\'eseau \path{docker-compose} --- coh\'erent avec l'absence de Dockerfile r\'eel pour ce service, mais cela signifie que ce service ne peut, \`a ce jour, \^etre v\'erifi\'e que depuis la VM cible elle-m\^eme, jamais depuis un environnement de d\'eveloppement local standard.
\end{itemize}

\section{Prochaines \'etapes sugg\'er\'ees}
% =====================================================================

Priorisation fond\'ee sur ce qui bloque le plus l'avancement d'un pipeline A1\textrightarrow A6 \emph{r\'eellement} bout en bout (et pas seulement au sens machine \`a \'etats) :

\begin{enumerate}[leftmargin=1.5em]
\item \textbf{Brancher \path{extracteur-evp} et \path{compliance-validation} sur une route API.} Les deux ont d\'ej\`a un code m\'etier complet et test\'e (16 + 28 tests) : c'est le rapport effort/valeur le plus favorable de tout le d\'ep\^ot. Sans cette \'etape, aucun appel inter-services n'est possible, quel que soit l'avancement de l'orchestrateur.
\item \textbf{Faire appeler r\'eellement ces routes par l'orchestrateur} lors des transitions correspondantes (\path{extraire_evp} $\to$ appel HTTP \`a \path{extracteur-evp}, etc.), pour que le pipeline A1\textrightarrow A6 traite un dossier r\'eel et pas seulement un changement de statut.
\item \textbf{\'Ecrire un mock minimal pour \path{integration-sage}} (m\^eme un calcul factice d\'eterministe) : c'est aujourd'hui le seul maillon du pipeline sans aucune logique, et A3 (calcul) en d\'epend directement.
\item \textbf{Ajouter des tests automatis\'es pour \path{rag/}} (au moins des tests unitaires sur \path{chunking.py}, qui ne d\'ependent pas de Qdrant/Ollama), pour sortir ce service de la situation ``0 test'' actuelle avant qu'il ne grossisse davantage.
\item \textbf{Fixer un Dockerfile r\'eel pour \path{rag/}} et le brancher sur \path{docker-compose.dev.yml}, pour que ce service soit v\'erifiable en local et pas seulement sur la VM cible.
\item \textbf{Mettre \`a jour \path{README.md}} avec un \'etat r\'eel minimal (m\^eme un lien vers ce document), pour qu'un nouvel arrivant n'ait pas \`a d\'eduire l'\'etat du projet du seul historique Git.
\item \textbf{Documenter la proc\'edure de d\'emarrage local} (valeurs \path{DATABASE_URL} r\'eelles, n\'ecessit\'e de \path{--build} pour \'eviter de servir une image p\'erim\'ee) pour \'eviter la r\'ep\'etition du probl\`eme d\'ecouvert en \S\ref{sec:dette}.
\end{enumerate}
